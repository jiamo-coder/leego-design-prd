# 面向经营决策的需求提问

用于需求探索、重大变更或关键矛盾未解时。目标是让问题帮助用户做选择，不以问题数量证明专业。相关方法：GL-024、GL-026、GL-027、GL-028。

## 先读，再问

先查当前项目 PRD、决策和用户最近纠正，区分：已确认事实、待选择规则、可核验实现、可逆建议。确认过的不重复问，能查到的不让用户抄文件；例如已经明确“只用账号密码”，不能再问要不要短信登录。

先给简短理解/功能表，再只问最影响下一步的一至三个问题；这不是固定问卷，信息足够时零问题。用户只回答部分时继续不依赖答案的内容；确实会改变付款、权限、数据归属或核心流程的空白不能悄悄默认。

## 问会改变方案的问题

| 未知点 | 比抽象问法更有效的问法 | 回答改变什么 |
|---|---|---|
| 价值与对象 | 这次优先让店员少录一次、让采购少漏单，还是让老板更早看出缺货？当前最痛的是哪一步？ | 首要角色、入口与验收指标；不是强迫三选一，可接受其他目标 |
| 权责与资金 | 门店提数量以后，谁决定供应商/价格、谁付款、谁确认实收？ | 采购主体、审批、数据可见范围与履约责任 |
| 模糊动作 | 你说“结算”，是核对货款生成结算单，还是要真的发起支付？ | 记录/确认与不可逆资金执行边界 |
| 真实流程 | 请用最近一张典型单说一下：谁发起、谁接手、什么证据才算完成？ | 状态、权威记录与角色，不要求提供不必要的真实隐私 |
| 异常分支 | 一单分两次到货，其中一批少收，剩余量谁确认补发或取消？ | 分批、差异、关闭与更正规则 |
| 范围选择 | 建议本期先把人工登记到核实做完整，自动支付后置；这样能先用起来，但仍需人工核实。是否符合这次目标？ | 明确取舍，不用技术名词让用户替工程师设计 |

这些是按缺口选用的例子，不要一次全部询问。给选项时解释收益、成本与风险，表明推荐理由；允许用户推翻选项，不将推荐当成已授权。

## 什么时候继续、什么时候停

- 无阻塞：直接形成速览和 PRD，不再请用户确认“是否开始写”。
- 可逆细节：明确“建议/暂定”并继续，例如表格列序；不编造未知价格、角色或默认支付授权。
- 核心未决：只暂停依赖该决定的部分，展示具体问题、影响及推荐；其他模块继续。
- 用户要求先确认方向：先短表加关键问题，不抢先编码；收到明确确认后继承授权，不重复同一轮确认。
- 用户已要求直接交付：按已知事实出稿，待定项集中列出，不以问诊形式制造签字门槛。

## 吸收回答

用户纠正后用一句话或小表说明“这次改什么、什么保持不变、影响哪些需求/验收”，更新当前 PRD 与获授权的项目记忆，保留旧决策取代关系。历史 Web 优先、某项目不占库、仅密码登录等结论不是新项目的通用答案。

提问质量由是否消除方案歧义判断：应能把回答转为范围、角色、状态、金额/数量规则或验收差异；不能改变任何判断的问题通常不必问。没有结果数据时不宣称提问已提高转化率或开发效率。

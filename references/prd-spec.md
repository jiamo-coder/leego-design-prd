# Codex 可实施 PRD 规范

在起草、补全或评审 PRD 时使用本规范。根据产品复杂度裁剪章节，但不可省略影响范围、权限、数据或验收的内容。

## 首个正文板块：本次需求速览

这是用户明确要求的默认阅读顺序，适用于确认稿、正式 PRD 和重大修订。标题下可放一行版本/状态，随后先给短列表或功能表，**不要先放长元数据表、背景论述、调研过程或技术架构**。

- 小需求用短列表，每项包含动作与结果；多角色/多模块用精简功能表，按业务闭环归组，不把全部细项挤到首页。
- 先用一句话说明“服务谁、改善什么业务结果”；表格建议用下列四列，按任务裁剪，不强制凑条数。

| 功能/业务场景 | 谁使用、完成什么 | 本期范围与边界 | 确认状态/对应需求 |
|---|---|---|---|
| 例：门店叫货 | 店长提交数量和到货需求，采购核对后处理 | 本期先核对提交；不代表已经订货或入库 | 示例，实际稿按真实状态和 FR 编号填写 |

表后只放会改变当前方案的少量待定项或一句本期不做。正文再补规则、异常与验收。若没有未决项，不人为添加确认问题或要求用户再签一次字。

速览是正文的投影，不是另一套口径：保留对应需求编号/小节指向，不能把“建议”写成“已确认”，不能因简短而隐藏金额、权限、责任和当前阶段。用户仅要清单时就交清单，不附完整长 PRD；用户指定其他格式时服从指定格式。

修订稿先用“新增 / 调整 / 不变”简表说明业务与交付影响，保留稳定 ID 与旧决策取代关系。这里的“先”是阅读顺序，不要求未消除的高风险问题被默认为已解决。

## 文档状态

在速览之后维护必要元数据（简单需求可合并为一行）：

| 字段 | 内容 |
|---|---|
| 产品/需求名称 | 唯一、可搜索的名称 |
| 文档状态 | 探索中 / 草案 / 待评审 / 已确认·可开发 |
| 版本 | 例如 `v0.1`；已确认后变更需递增 |
| 负责人/决策人 | 未知则标 `待确认`，不要虚构 |
| 更新时间 | 使用明确日期 |
| 需求来源 | 访谈、旧系统、工单、文档等 |

已存在基线时增加变更记录，说明版本、日期、变更项 ID、原因、影响和决策人。

## 推荐结构

### 1. 本次需求速览

- 采用上面的短列表或功能表，先呈现服务对象、业务价值、本期范围与确认状态。
- 付费产品交代收入机制与成本承担；内部工具交代经营改善或风险控制。具体金额未知就标假设，不补造 ROI。
- 完整成功口径、规则和验收在正文展开，不重复首页表格。

### 2. 背景与现状

说明当前业务流程、参与者、系统、数据来源、痛点及证据。区分客观事实和判断。不要只写“效率低”，应说明发生在哪一步、影响谁、频率或后果是什么。

### 3. 术语、参与者与权限边界

- 给业务术语和关键数据口径下定义。
- 列出角色职责；组织层级和多租户场景需说明数据隔离边界。
- 有差异权限时提供矩阵：角色 × 动作 × 数据范围 × 限制条件。

### 4. 范围与优先级

分别列出：

- `P0`：缺失则业务闭环不可成立或无法上线。
- `P1`：本期重要，但必要时可以单独降级或延期。
- `P2`：明确放入后续候选，不进入本期承诺。
- 非目标：容易被误认为包含、但本期明确不做的内容。

优先级必须落到具体需求，不能只给模块定性。

### 5. 业务流程与使用场景

对每个关键场景使用稳定 ID，如 `UC-01`，至少说明：

- 参与角色、前置条件和触发事件
- 主成功路径
- 可预见的分支、异常和人工兜底
- 结束状态及对其他角色/系统的影响

复杂流程增加状态迁移表：当前状态、触发动作、条件、下一状态、执行者、失败处理。禁止出现无入口、无出口或无法恢复的状态。

### 6. 功能需求与业务规则

功能需求使用 `FR-001` 等稳定 ID。推荐字段：

| ID | 优先级 | 角色 | 需求与业务价值 | 前置/触发 | 结果 | 关联规则 | 验收 |
|---|---|---|---|---|---|---|---|

业务规则单独使用 `BR-001` 等 ID，尤其是计算、唯一性、时限、权限、状态、互斥、重复提交和追溯规则。规则应覆盖边界值，并注明口径或决策来源。

一条需求只表达一个可独立验证的行为。使用“当……时，系统应……”等明确句式，禁止使用没有阈值的“快速”“大量”“实时”“智能”“友好”。

### 7. 数据、集成与审计

按需说明：

- 核心业务实体、字段含义、必填性、唯一性、枚举、校验和生命周期。
- 数据创建者、所有者、可见者、修改者、归档/删除规则和保留期限。
- 存量数据迁移、导入导出格式、重复数据和失败数据处理。
- 上下游系统、数据权威源、同步方向、触发方式、时效、幂等、重试、超时、对账和降级。
- 必须记录的关键操作、前后值、操作者、时间、来源及审计查询权限。

PRD 定义业务所需的数据语义与约束；未经确认不要发明数据库表、接口路径或字段协议。

### 8. 页面与交互要求

列出信息架构、页面/入口、核心操作和反馈。每个关键界面考虑：加载、空数据、错误、无权限、部分成功、重复操作、并发冲突和超时状态。

只有确有必要时描述布局或控件。PRD 负责交互目标和业务约束，不替代视觉稿。

### 9. 非功能需求

只收录对本产品有业务意义且可以验证的约束：

- 性能：数据规模、并发前提、响应时间或批处理时限。
- 可用性：服务时段、允许中断、失败恢复、备份与恢复目标。
- 安全与隐私：认证、授权、敏感字段、传输/存储、脱敏、导出限制。
- 兼容与可访问性：目标设备、浏览器、系统版本、语言或辅助使用要求。
- 可运维性：配置、告警、日志、问题定位、业务补偿和运营责任人。

不能确定阈值时写成待确认问题并说明其对架构或排期的影响，不使用随意数字填空。

### 10. 验收标准

验收项使用 `AC-001` 等 ID，并反向关联需求 ID。P0/P1 的主流程、权限限制、关键异常和边界值都要有验收覆盖。

优先使用可执行语义：

```text
AC-001（关联 FR-001、BR-002）
Given 已登录用户属于华东区且仅有本区域数据权限
When 用户打开订单列表
Then 列表和汇总数据仅包含华东区订单
And 直接访问其他区域订单地址时返回无权限状态且不泄露订单内容
```

不要把“页面开发完成”“符合设计稿”或“功能正常”作为验收标准。

### 11. 发布、迁移与运营

说明上线前置条件、配置或初始化责任、存量数据迁移、灰度范围、回滚条件、兼容期、用户通知/培训和上线后观察指标。只有用户明确需要采集时才提出新的埋点或分析能力。

### 12. 依赖、风险、假设与待确认项

分开列出四类内容。每个待确认项包含：问题、为什么重要、影响的需求 ID、建议负责人和最迟决策点。高风险假设不能藏在正文中。

### 13. Codex 实施摘要

用最短篇幅重申：范围、排除项、需求/验收 ID、技术与仓库约束、数据迁移、外部依赖、发布约束和编码阻塞项。该摘要用于导航，不能取代正文。

## 质量检查

交付前逐项检查：

- 每个目标是否有对应需求或成功口径；每个 P0/P1 需求是否服务某个目标。
- 首个正文板块是否可快速读懂本期做什么、不做什么及谁受益；短表是否与详细需求、阶段和确认状态一致。
- 是否说明谁承担成本、履约与异常损失；是否把业务金额、平台服务费及实际收付混为一谈。
- 相同概念是否始终使用同一术语、状态和数据口径。
- 角色是否可能通过入口、URL、导出或接口越权看到/修改数据。
- 主流程是否覆盖撤回、驳回、取消、重复、超时、失败和恢复等相关路径。
- 需求 ID、规则 ID、场景 ID 与验收 ID 是否能相互追踪。
- 是否把产品建议或技术猜测误写成已确认事实。
- 是否存在需要 Codex 自行猜业务规则才能编码的句子。
- “已确认·可开发”文档是否真的没有阻塞 P0/P1 的开放问题。

评审现有 PRD 时按严重程度输出：

- `阻塞`：无法确定范围、权限、数据、核心规则或验收，直接编码风险高。
- `重要`：不阻塞主路径，但可能导致明显返工、异常或运营问题。
- `优化`：清晰度、一致性或维护性改进。

每个问题必须指出位置/ID、具体风险和最小修订建议，不只给抽象评价。

## 对话式 AI 员工与 Bot 交接

适用于行业助手壳、聊内办单、Bot 舰队或 PRD→UI→实现分工的需求。可按产品裁剪，但涉及下列能力时不可省略。

- **壳与信息架构**：是否采用侧栏名册 + 对话 + 可收缩预览；浅色/深色默认；移动等价入口；行业底栏/根导航哪些硬锁不可删。
- **聊内作业**：确认卡/表单的过程态、幂等、过期与重新发起；预览挂载与受限工件；打开预览 ≠ 授权写入。
- **运行环境与模型**：目标部署网络主路径、主引擎列表、会话引擎 vs Bot 默认、禁用与降级；模板全球分发 ≠ 境外主引擎。
- **主数据与契约**：权威源表；字段契约（语义 ID ≠ 库列名）；路由规则与缺关系处理；待对照 schema 清单。
- **状态与文案**：需求/下单/到货/收货/过账等是否可区分；NL 摘要最低字段集；深链策略；反虚构条款。
- **分发与通知**：通道配置、回执、失败重试/换通道、失败是否撤单；未拍板通道标待对照，占位不计入验收。
- **舰队与人效（若有）**：嵌壳方式、可交付物定义、暂停/继续、互唤同意、额度与失败通知。
- **交接与授权**：PRD / UI 预览包 / Codex 摘要各自职责；是否「只碰前端」；是否授权公开入口覆盖发布。
- **标记纪律**：全文区分 `已确认` / `产品建议` / `临时假设` / `待确认`；产品建议不得写成用户签字。
